# 监测、阶段提醒与运行回执

## 先选择策略，再启动监测

读取现有计划与用户偏好，区分一次盘点、定时检查和持续循环；可按来源混合，但不要重复运行同一职责。核对每个来源、时区、时间窗、频率或轮间等待、通知对象/渠道、有效期和停止条件。持续扫描使用用户明确确认的监测授权；一次性请求以本轮结果交付。

定时检查可选择的示例：邮件每 30 分钟；网页来源白天 08:00–20:00 每小时；夜间每小时或仅紧急事项；低频会议平台每天一次。频率、白夜边界和夜间通知方式须由用户选择；摘要也可按用户选择的时点（例如 10:00 和 22:00）发送，并保存为该用户的配置。若已有偏好则沿用，不反复询问。

区分计划触发频率、实际执行时间和通知送达时间；按本轮实际读取时间记录覆盖终点，同时记录提前触发、执行延迟和通知时间。遇到平台额度、网页登录到期或任务调度变化时，更新健康状态与恢复提示。

创建/调整后记录提供者的计划 ID、已保存状态、时区、下一次预定执行。再读取计划验证，不以创建请求已发送为证据。持续任务具有明确范围与停止条件；修改或取消只在授权范围内进行。

## 可选持续循环：每个来源独立只读

只有用户明确选择后才启动。为每个授权来源分配一个独立只读 worker，明确来源、允许的页面/对象、观察窗口、基线、唯一标识及停止条件。多个来源可并行，同一来源按轮串行执行，每轮完成后等待配置间隔再开始下一轮。典型轮间等待可取 300 秒；将本轮耗时、退避等待和调度情况一并计入实际检查节奏。

浏览器 worker 各用独立标签页、唯一变量和页面句柄，只操作自己绑定的来源；保持各 worker 的导航、变量和页面状态相互独立。若环境无法可靠隔离，则降低并发或改为串行读取，并如实说明；使用为该来源分配的页面，保留用户及其他任务的页面状态。日历写入继续由单一写入者按独立授权执行，与监测职责分离。

由主协调者维护跨来源事项与通知台账：worker 回传证据、稳定来源 ID、实际读取范围和状态；主协调者合并后通知。用户选择“所有新增立即告知”时，通知所有授权范围内的核实新事项/实质更新，包括普通事项；每个来源核实并去重后即交付，早晚汇总另行汇整。将已有基线条目、未读变化、重复投递和跨源同一事项合并到原记录；completed/dismissed 规则继续有效。

首次成功后报告该来源已建立的实际基线及覆盖；首次阻塞也立即报告具体环节。基线里的旧事项可列入初始积压盘点，临近事项仍可提醒，并标明“首次盘点发现”。基线待建立时标为 baseline_pending，建立后按增量判定新增。

每轮记录 run_started_at、run_finished_at、coverage、last_success_at、next_check_at（预期）、结果及失败原因；时间带时区。把 worker 状态与数据读取状态分别记录，以成功回执累计全天已覆盖区间，列明待恢复缺口；next_check_at 保持为预期时间。

瞬时网络/页面故障每轮有界重试（默认最多一次），后续轮按合理退避等待；记录延后原因，避免紧密重复请求。认证失效、访问拒绝或缺少权限时暂停该来源，报告所需用户操作/新授权，按受支持的认证和授权流程恢复；其他获准且正常的来源继续。恢复后从该来源 last_success_at/游标补查缺口并去重，并区分补扫旧记录与真正新增。

环境、会话/上下文或 worker 中断时，记录中断位置与覆盖缺口。持久化运行、重启和替代方案按当前授权配置，完成实际恢复测试后记录结果。用户取消旧定时兜底时，定位对应重复计划并回读停用结果，同时保留指定的会议检查与早晚汇总；恢复已取消项时重新取得同意。用户停止、撤权或到达约定终点时停止对应循环；一轮完成后按已选节奏进入下一轮，直至约定停止条件成立。

## 可配置案例：复旦四源循环 + 腾讯会议定时

以下提供一组可直接选择或调整的配置；启用后按实际回执显示运行状态：

| 职责 | 来源/安排 | 节奏与时区 |
|---|---|---|
| 四个独立只读循环 | Gmail、复旦邮箱、复旦 eHall、复旦 eLearning | 各轮完成后等待 300 秒再查，全天持续循环；记录各源实际覆盖与恢复状态 |
| 会议检查 | 腾讯会议 | 每天 10:00、22:00，Asia/Shanghai（北京时间） |
| 早晚汇总 | 汇总所有获准来源与监测健康 | 每天 10:00、22:00，Asia/Shanghai；同时保留新增即时通知 |

采用此案例前逐一确认来源与授权。其他学校/组织可替换来源，用户可选择不同等待时间、时点和停止条件；沿用已有明确偏好，不要求重复授权。腾讯会议沿用所选定时模式；早晚汇总与会议检查即使同一时点也分别记录职责与实际结果。用户要求只留循环加这些指定时点时，停掉被替代的旧轮询/兜底计划，保留指定任务并验证没有重复。

## 阶段提醒

可向用户提供 7 天、3 天、1 天、当天和开始/截止前 2 小时的分阶段方案；按事项类型、重要性和用户偏好开启，而非全部默认打开。

- “当天”使用用户选择的摘要时刻，不能偷偷增加通知。
- 小时级提醒只有在钟点与时区均明确时才创建；date-only 截止不推定 00:00 或 23:59。
- 已过去阶段不集中补发；首次发现临近事项时发送一次当前紧急摘要，再计划仍适用的未来阶段。
- 同一事项跨来源只发一次相同阶段/渠道的提醒。已完成或 dismissed 的事项停催；修改截止后取消/使旧阶段失效，保留审计记录。
- 对已核实的紧急事项，在取得该来源证据后立即发出当前渠道内且已授权的提醒，不等待其他来源全量检查结束。若来源仍有冲突，明确不确定性，不作虚假确定判断。

## 每轮运行

1. 读取授权范围、最近检查游标及处置/提醒台账。
2. 按来源读取增量，必要时用重叠窗口避免漏项；保存真实尝试和成功时间、覆盖及失败。
3. 提取、合并、检查用户处置；先报告紧急项。若选择所有新增即时通知，则所有核实新增都立即交主协调者去重通知，不等汇总；只读监测本身不执行日历修改。
4. 验证写入与提醒动作，记录实际回执。失败步骤采用有界重试，不重复发送不确定的通知；先查发送记录，无法确定则标记待核查。
5. 返回简洁回执并推进成功来源的游标；失败来源保留上次成功位置，恢复后补扫缺口。

将“没有新事项”限定到成功覆盖的来源和时间段。部分失败时写“邮件已查至某时无新增；课程平台本轮未能读取，上次成功为某时”，保留各来源独立状态。

## 验收与交接

记录四种不同证据：计划设置回读、实际运行回执、日历事件提醒字段回读、设备收到通知（用户确认亦可）。待首次运行时写“计划已设置，首轮待验证”；设备测试前写“提醒已配置，送达待测试”。测试通知按用户确认的对象、渠道与时间发送。

回执包含：各来源实际开始/结束时间与时区、成功/部分/失败状态、覆盖范围、last_success_at、已通知新增及紧急项、增改/核验/跳过数、待确认项、下一次预期检查和仍未验证的环节。早晚汇总还列出各来源健康、阻塞和覆盖缺口，将尚未读取的来源列为待检查。持续运行中出现授权到期、来源失效或范围外变更时暂停对应部分并请求处理，明确给出恢复提示。
