# 日历写入与验收

## 写入前

- 核对用户授权的账户、私有日历、动作范围（创建/更新/删除）及提醒策略。创建一个新日历本身也是变更，需有授权；不添加参与者，不发送邀请。
- 通过 ID/UID 和相邻日期窗口检索已有事件；来源变更尽量更新已关联事项，不另建重复副本。先检查已完成/忽略台账。
- 验证事件时区与界面显示时区。需要打开“时区支持”或更改全局设置时先确认用户同意，记录变更前值和影响；不能仅为方便写入而静默改设置。
- 确定开始、结束、精度与重复条件。未知结束时间时，优先用明确标注的开始提醒；若工具必须有结束，向用户确认临时时长，并在标题/备注和台账标为 provisional，不能把方便填写的时长伪装为真实会议安排。
- 使用平台明示的 future recurrence、count/until、取消及例外。只根据历史推断的重复候选须遵循用户选择的规则且获确认；无限期默认不合适时暂停询问结束条件。

## 浏览器执行

1. 让一个写入者独占当前日历编辑界面；其他研究只读且不能操作相同标签页。
2. 打开编辑器并核对目标日历；设置日期/时区/钟点等字段，每次可能触发异步刷新的操作后，重新读取界面确认完成再执行下一个依赖操作。切换时区可能改变显示钟点，不能在未稳定时继续输入。
3. 设置重复、终止和提醒时分步打开、读取选项、选择、重新读取；不要凭旧坐标/旧快照连点。
4. 保存后退出编辑器，从列表或日期位置重新打开该事件。逐个检查所有事件，而不是只抽查第一项。需要修改时重复保存和重新打开验收。

## 每个事件的回读字段

目标日历；标题/来源关联；日期；全天或定时；事件时区；开始/结束和跨日；重复频率、区间、次数或结束日期；排除日期；提醒时间/渠道；无意外参与者或共享。

同时比对用户当地显示与规范化时间。例如真实来源为中国时间 19:00，若显示在日本时区应为 20:00；只有确认两端时区后才换算一次。不要仅凭地点名列表猜测事件已经变更。

记录 event_id/稳定定位方式、verified_at、回读值与结果。保存按钮成功、列表新增标题、API 返回 ID 都是中间证据，不能替代字段核验。

## 不确定结果和重试

默认每个失败步骤最多重试一次；仅对已理解的临时故障、在既有授权内、且没有不确定的重复写入风险时重试。先刷新并按 ID、标题/时段、目标日历检索，再决定是完成核验、修正现有事件还是确实重建。

若保存返回超时或页面无反馈，先查证现存结果，不能马上再点保存。无法确定是否创建成功时标记 write_uncertain，暂停该项并报告；禁止盲目重建。遇到权限拒绝、登录失效、时区始终不符或重复错误，停止依赖写入，保留证据并请求必要处理。

## 交付计数

区分 proposed / created / updated / verified / skipped / write_uncertain / failed；“新增 5 项”只有核验 4 项时必须明确写成“4 项已核验，1 项待核查”，而不是“已完成 5 项”。
